# 公开发布与 VPS 部署

## 背景

游戏本体（单机 + 联机 1v1）已可用，但从未离开过开发机。现在要把它放到一台
自有 VPS 上给玩家访问，并把仓库公开到 GitHub —— 公开的直接动机是能用
GitHub Actions 构建镜像、GHCR 托管，省掉在 2C4G 机器上跑 vite 构建。

## 目标

1. 仓库具备公开条件并完成公开
2. 一条 `docker compose up -d` 量级的部署路径，含 TLS 与反代
3. 在 5Mbps / 500GB 的约束下，让实际游玩体验不被带宽拖垮

## 硬约束

| 项 | 值 | 影响 |
|---|---|---|
| CPU / 内存 | 2C4G | 不是瓶颈；无数据库、房间全在内存 |
| 出站带宽 | **5 Mbps ≈ 600 KB/s** | **真正的瓶颈**，见下方测算 |
| 月流量 | 500 GB | 约 12,500 人·小时，对朋友局宽松 |
| 系统盘 | 60 GB | 宽松：assets 228M + node_modules 141M + 镜像 ~200M |
| 归属地 | **境内，域名已备案** | 国内 CDN 可用；80/443 可用 |

### 带宽测算（实测字节数，非估计）

| 项 | 字节 | 依据 |
|---|---|---|
| 冷启动首屏 | **≈ 5.0 MB** | JS 327K + CSS 31K + `bg/loop.mp4` **4.15M** + sfx 6 个 WAV 300K + brand 96K + 一条 greet ~70K |
| 环境 BGM | **≈ 10 KB/s** | 3~4 切片 × 148K ≈ 520K / 45~60 秒（80 kbps opus） |
| 对局每回合 | ≈ 200 KB | clip 148K + 封面 49K |

两条推论：

- **并发**：600 KB/s ÷ 10 KB/s ≈ 55~60 人在线。但先撞墙的是冷访问——
  一次 5MB 首屏**独占整条线 8 秒**，三人同时首访即 25 秒黑屏。
- **月流量**：500 GB ÷ ~40 MB/人·小时 ≈ 12,500 人·小时。不是主要矛盾。

因此优化优先级是**削首屏突发** > 削稳态。

## 已确认的决策（用户拍板，不再重开）

1. **仓库公开，第三方素材照留。** `apps/web/public/` 下 94 个素材
   （57 greet 语音 / 29 idol 图 / 7 emote / `bg/loop.mp4` / brand / mark）
   均为万代南梦宫版权素材，`design-extract-output/` 的设计语言文档源自官网。
   风险已明确告知（含与备案实名信息可关联这一点），用户确认照此执行。
   干净的只有 `sfx/`（CC0，附 CREDITS.md）。
2. **境内 VPS + 已备案域名**，因此走国内 CDN 而非 Cloudflare。

## 子任务地图

| 子任务 | 边界 | 依赖 |
|---|---|---|
| `08-31-oss-repo-prep` | 公开前的仓库形态：README / LICENSE / `.github` / 归属声明 / 历史与工作区的敏感信息审查 / 既有文档在公开语境下的措辞复核 | 无。**必须最先完成**——仓库一旦公开，历史不可撤回 |
| `08-31-docker-deploy` | Dockerfile / compose / Caddy / GHCR CI / assets 同步与 VPS 侧操作手册 | GHCR 部分依赖仓库已公开（公开包才有免费带宽） |
| `08-31-cdn-and-bandwidth` | CDN 选型接入 + 首屏与稳态的字节削减 | 压缩项与 Caddy 配置在 `docker-deploy` 里落地，需协调 |

排序理由：`oss-repo-prep` 是不可逆动作的前置检查，必须先做完。
`docker-deploy` 与 `cdn-and-bandwidth` 有一处交叠（响应压缩放 Caddy 还是 CDN），
在 `docker-deploy` 的 design 阶段定归属，另一侧只引用不重复实现。

## 跨子任务验收标准

- [ ] 仓库在 GitHub 上公开，`git log --all` 与工作区均无凭据、无 `.env`、无个人隐私信息
- [ ] 第三方素材的来源与权属在 README 中有明确声明
- [ ] 从零开始的部署：clone → 同步 assets → `docker compose up -d` → 域名可 https 访问
- [ ] `DEPLOY.md` 的检查清单逐条通过（尤其 wss 连通、记忆阶段 30 秒不掉线、切片响应无 `Last-Modified`）
- [ ] 冷启动首屏字节数 **< 2 MB**（当前 5.0 MB）
- [ ] 服务端响应带压缩（当前 327KB 的 JS 是裸发的）
- [ ] CDN 接入后 `/ws` 仍能建立连接且不被中断（这是最容易踩的一条，见 cdn 子任务的研究结论）
- [ ] 切片响应仍为 `no-store`，且**不经 CDN 缓存**

## 明确不做

- 不引入数据库或持久化（房间在内存、重启即丢是既有设计，不在本次范围）
- 不做多机 / 高可用 / 自动扩缩
- 不改动曲库保密红线（private manifest 不出 HTTP、切片一次性 token、no-store）
- 不生成 AAC 兜底副本（`DEPLOY.md` 有独立流程，按需另行决定）
