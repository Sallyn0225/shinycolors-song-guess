# 技术设计：桌面端全站密度与版心收紧

## 改动边界

只有两类文件会被改：

| 文件 | 改什么 |
|---|---|
| `apps/web/src/index.css` | `--u` 的桌面公式、版心 token、`.sc-song` / `.sc-bar` / `.sc-options` / `.sc-revealslot` 的桌面值 |
| `apps/web/src/screens/{Start,Play,Result,Lobby,Room,Karuta}.tsx` | 把内联 `maxWidth` 换成 token；`Start` 与 `Play` 的纵向节奏类名 |
| `apps/web/src/screens/Play.tsx` | 揭晓块的曲名单行化 |

`src/audio.ts`、`src/net/ws.ts`、`src/api.ts`、`src/features/*` 不动。`ui/*` 与 `components/*` 除 `OptionBar` 之外不动，且 `OptionBar` 只借 `.sc-*` 类换尺寸，组件本身不改结构。

## 决策一：`--u` 同时受宽和高约束

现状：

```css
:root { --u: clamp(0.78px, 0.0694444444vw, 1.16px); }
```

`0.0694444444vw` 就是 `视口宽 / 1440`。设计稿是 1440×900，但公式只看宽——所以在一块 1920×1080 的屏上 `--u` 取到上钳位 1.16，一切放大 16%，而视口高只有 990px（比稿高多 10%），放大 16% 的内容必然溢出。宽高的比例一旦偏离 16:10，纯按宽缩放就一定会在某个方向撑爆。

改为：

```css
:root { --u: clamp(0.78px, min(0.0694444444vw, 0.1111111111vh), 1px); }
```

`0.1111111111vh` = `视口高 / 900`，与 `vw` 项取 `min()`——这就是「把 1440×900 的稿等比装进当前视口」的标准写法，两个方向都不会溢出。上钳位从 `1.16px` 降到 `1px`：`index.css` 的注释本来就写着「1440 处 --u 恰为 1px，即官网的 1:1 还原点」，允许超过 1 等于允许版面比它自己的参考稿还大，那正是「元素都比较大」的来源。

实测各档取值（视口高 = 屏高 − 90）：

| 屏幕 | 旧 `--u` | 新 `--u` | 变化 |
|---|---|---|---|
| 1366×768 | 0.949 | 0.780（触底钳位） | −18% |
| 1440×900 | 1.000 | 0.900 | −10% |
| 1536×864 | 1.067 | 0.860 | −19% |
| 1920×1080 | 1.160 | 1.000 | −14% |
| 2560×1440 | 1.160 | 1.000 | −14% |

**为什么可以让字号跟着视口高变。** 因为最小的两级字号带真 px 地板（`--text-2xs` 11px、`--text-xs` 12px），触摸热区是真 px 44px，发丝线恒 1px——`--u` 变小击穿不了任何一条可读性下限。这三条地板本来就是为了低钳位场景设的，这次只是让低钳位更常触发。

**为什么 `@media (max-width: 767px)` 那条不改。** 移动端浏览器地址栏收起会改变 `vh`，把字号绑到 `vh` 上会在滚动时抖动。窄屏规则只有 `vw` 项，保持原样。

**副作用（接受）。** 桌面端改变浏览器窗口高度会等比改变字号。这在一个「按稿等比缩放」的设计系统里是既有语义的延伸，不是新行为——横向早就是这么做的。

## 决策二：版心宽度收成 token

现状是三个字面量散在六个 screen 里（`1300u` ×3、`760u` ×2、`1000u` ×1）。收成 `:root` 上的命名 token：

```css
--page-main:   calc(1120 * var(--u));  /* 首页 / 单人猜歌 / 结算：多列信息 */
--page-board:  calc(1000 * var(--u));  /* 牌场：12+12 张牌的网格 */
--page-narrow: calc(760 * var(--u));   /* 大厅 / 房间：单列表单 */
--page-card:   calc(520 * var(--u));   /* 牌场结算卡 */
```

`1300u → 1120u` 是本次唯一改值的一档（−14%）。叠加 `--u` 从 1.16 降到 1.0，1920 视口下版心从 1508px 收到 1120px，两侧留白从各 206px 涨到各 400px（各占 20.8%，满足 AC4）。1440 视口下版心 1008px、两侧各 216px（各 15%），刚好卡在 AC4 的下限上——这是选 1120 而不是更小的原因：再窄，1366 档的四条选项条会短到失去「整宽横条」的形状语义。

其余三个 token 只是把既有字面量搬家，取值不变。

## 决策三：`Play` 的高度必须是常量

页面高度目前有两处随内容变：

**(a) 揭晓槽。** `.sc-revealslot { min-height: calc(58 * var(--u)) }`，但揭晓内容的实际高度：

- 左侧封面 `56u`
- 中间：曲名 `22u`（无 clamp，长标题会折行）+ 演唱者 `text-sm`
- 右侧：「正解」`26u` + 「+N 速度 +M」`text-sm` ≈ `58.5u`

右侧那一列**本来就超过** `58u`，所以每次揭晓页面都长高一点；曲名折行时再多长 `33u`。

改法两步：

1. 桌面下把 `.sc-revealslot` 从 `min-height` 改成**定高** `calc(64 * var(--u))`。64 覆盖住最高的一列（58.5u）并留出余量。
2. `Play.tsx` 里揭晓块的曲名加 `truncate`（单行 + 省略号），使中间列恒为「一行曲名 + 一行演唱者」≈ `52.5u`，不再可能超过 64u。

窄屏那条 `.sc-revealslot { min-height: calc(38 * var(--u)) }` 不动——移动端上这一块本来就要能换行。

**(b) 选项条。** `.sc-bar` 是 `min-height: max(60px, calc(112 * var(--u)))`，而条内文本块 = `.sc-song` 32u × lh 1.22 × 最多 2 行（`line-clamp-2`）+ `mt-0.5` + 演唱者 14.5u ≈ `101.75u`。两行曲名的条被内容顶到 102u，一行的停在 112u——所以 112u 这个钳位其实同时**掩盖**和**没掩盖**问题：钳位足够大时高度一致，但一旦 `--u` 变小、真 px 地板 `60px` 反超，两者又会错开。

改法：`.sc-song` 桌面从 `32u` 降到 `28u`（两行 = 68.3u，加演唱者与间距 ≈ 92u），`.sc-bar` 桌面改成**定高** `max(60px, calc(96 * var(--u)))`。92u < 96u，所以无论曲名一行还是两行，条恒为 96u。窄屏的 `sc-song: 22u` / `sc-bar: max(56px, 74u)` 不动。

顺带 `.sc-options` 的 `gap` 从 `20u` 收到 `16u`。

**纵向预算核算**（1440×810，`--u` = 0.9）：

| 段 | 旧 | 新 |
|---|---|---|
| `py-8` ×2 | 57.6 | 57.6 |
| header（SectionTitle + 计数） | 64.7 | 64.7 |
| `mt-5` + PrismRail `112u` → `88u` | 118.8 | 97.2 |
| `mt-4` + 揭晓槽 `58u` → `64u` | 66.6 | 72.0 |
| `mt-2` + 4×条 + 3×gap | 464.4 | 397.8 |
| `mt-6` + 主按钮 + `pb-6` | 99.0 | 99.0 |
| **合计** | **871** | **788** |

788 < 810 ✓。1366×678 档（`--u` = 0.78）同法核算约 661 < 678 ✓。

PrismRail 的频谱带 `112u → 88u`：那 112u 是频谱的动态范围上限（组件注释里写明 comp 的频谱带约 140px），88u 在 1440 档仍有 79px 的峰高，不会「摊成栅栏」。这一档是**桌面专属**，通过 `.sc-rail-spectrum` 类下放到 CSS，而不是改组件里的 `span` 常量——组件那个三分支（`mirror` / `spectrum` / 线）的语义要留着。

## 决策四：`Start` 的纵向节奏

`Start` 的段间距是 `py-14` / `mt-14` / `mt-12` 三档，在 1440×810 下合计约 907px。桌面把它压到 `py-10` / `mt-10` / `mt-9`，并把 `EntryBar` 的 `minHeight` 从 `max(72px, 118u)` 收到 `max(72px, 104u)`——三条入口共省 42u。核算后约 800px，落在 810 之内。

这些是 Tailwind 工具类，直接改类名即可，不需要新 CSS。

## 风险与回退

| 风险 | 处理 |
|---|---|
| `--u` 绑 `vh` 后，某些短窗口下字号偏小 | 真 px 地板兜底；AC6 明确验收 |
| 定高 `.sc-bar` 在字体未加载（Noto Sans JP 回退到 PingFang SC）时内容溢出 | 验证时禁用远程字体各测一次；`line-clamp-2` 已经封住行数上限 |
| 揭晓块曲名 `truncate` 后长标题读不全 | 该曲名同时出现在正确答案那条选项条里（`line-clamp-2`，两行），信息不丢 |
| 版心收窄后牌场 12 列网格被挤 | 牌场用的是 `--page-board`（1000u，不改值），且已有 768 断点下的 4→3 列重排 |
| 纵向预算是估算，实测可能差几十 px | 实现后用 Puppeteer 在四档视口实测 `scrollHeight`，据实测微调一轮（见 `implement.md` 的验证门） |

回退点：所有改动集中在 `index.css` 与六个 screen 的类名/内联样式，`git revert` 单次提交即可完全回到现状，无数据、无接口、无持久化状态涉及。

## 实测与设计的偏差（实现后补记）

`measure.mjs` 的 baseline 推翻了两条推导，都记在这里，别让下一个人再算一遍：

1. **「桌面上揭晓会撑高页面」在四档桌面视口里复现不出来。** 设计里按 lh 1.5 估算右侧
   「正解 + 加分」列约 `58.5u`、刚好超过 `58u` 的 min-height，实测是 `≤ 58u`——
   1366 / 1440 / 1536 / 1920 四档上答对与答错的 `scrollHeight` 完全相同。
   真正会撑高的是**窄屏**（390×844 实测 `+8`，曲名折行把 `38u` 的槽顶到 88px）。

   定高 `.sc-revealslot` 仍然做了：`58u` 是压在边界上的巧合而不是保证，`--u` 一变、
   字体一回退就可能翻过去。定高把「不会变」从巧合变成约束，成本是 6u。
   曲名 `truncate` 顺带把窄屏那 `+8` 也修掉了。

2. **`.sc-bar` 的 `min-height: 112u` 在桌面上没有产生高度不齐。** 实测四条恒为 `112u × --u`，
   因为曲名 `line-clamp-2` 后的文本块（`~102u`）始终没越过 `112u` 的钳位。
   高度不齐的是**窄屏**（375 档实测 `74 / 77.41` 两种值并存）。
   改成定高 `96u` 的收益因此主要在纵向预算（省 `64u`），把「恒等高」变成结构保证是附带。

3. **纵向预算的估算偏乐观约 110px。** 估算 1440 档 Play 为 871px，实测 980px。
   差在 `SectionTitle` 的角标框内边距、`Stat` 组件高度、以及各处 `line-height` 的实际值。
   最终靠 `sm:py-8 → sm:py-5`（Play）与首页六处 `sm:` 间距降档补上，两轮测量收敛。

4. **收紧之后出现了新的构图问题：内容装得下了，却仍顶着上边排，底部空出 150~180px。**
   加 `.sc-vfit`（`justify-content: safe center`）解决。`safe` 是关键——裸 `center`
   在内容溢出时会把顶部推出视口且滚不回来，这正是 `Start.tsx` 原注释「不用 justify-center」
   要躲的坑，现在有了正确的写法。
