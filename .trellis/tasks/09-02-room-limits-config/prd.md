# 公开/私人房上限配置与大厅房间数展示

## Goal

给部署者三个新旋钮：**能不能开私人房**、**公开房最多几个**、**私人房最多几个**；
并让大厅把「现在占了多少 / 上限是多少」直接说出来 —— 私人房不进列表，但要计入数字。

今天只有一个全局 `MAX_ROOMS=200`，公开房和私人房共用一个池子。这有两个洞：

1. 部署者无法只关掉私人房（比如一个只想做公开匹配的实例），也无法防止「私人房把池子占满、
   大厅一个公开房都建不出来」。
2. 大厅只显示「等人 N · 进行中 N」，玩家不知道离上限还有多远。建房被拒时收到的
   `服务器房间已满` 是这一刻才第一次出现的信息，之前界面上没有任何征兆。

---

## Requirements

### R1 · 三个新配置项（服务端，环境变量）

| 变量 | 默认 | 语义 |
|---|---|---|
| `ALLOW_PRIVATE_ROOMS` | `1` | 是否允许创建私人房间。`0` = 本实例只做公开房 |
| `MAX_PUBLIC_ROOMS` | 跟随 `MAX_ROOMS` | 同时存在的**公开**房间数上限 |
| `MAX_PRIVATE_ROOMS` | 跟随 `MAX_ROOMS` | 同时存在的**私人**房间数上限 |

- `MAX_ROOMS` **保留原语义**，仍是全局总闸；`MAX_ROOMS=0` 仍是「不改代码临时关停建房」的
  应急开关。三道闸同时校验：总数、公开数、私人数任一到顶都拒绝建房。
- 两个分类上限的默认值**跟随 `MAX_ROOMS` 的实际取值**（不是跟随它的默认值 200）。
  只配 `MAX_ROOMS=50` 的部署者，行为与今天完全一致，UI 上分母也自然是 50。
- 与既有配额旋钮一致：分类上限接受 `0`（= 关掉这一类房间），`ALLOW_PRIVATE_ROOMS`
  与 `MAX_PRIVATE_ROOMS=0` 是等价的两条路，服务端合并成同一个判断。
- 不新增 HTTP 端点、不新增持久化。

### R2 · 服务端按可见性限流建房

- `createRoom` 的校验顺序：**总闸 → 私人房是否开放 → 分类上限 → 单 IP 持有数 → 单 IP 频次**。
  先全局后个人的既有顺序不变（服务器整体过载时所有人收到同一条消息）。
- 私人房关闭时，`visibility: 'private'` 的建房请求被**拒绝**，不静默降级成公开。
  协议层 `visibility` 的默认值仍是 `private`（漏传字段的失败方向只能是「不暴露」），
  所以漏传字段的老客户端会撞到这条拒绝 —— 这是正确的失败方向。
- 拒绝时的提示必须能区分三种原因：服务器满了 / 这一类房间满了 / 本站不开私人房。

### R3 · 协议下发房间数与上限

`roomList` 增加私人房数量与两类上限，让大厅能显示占用情况。

- 公开房总数**不新增字段**：既有的 `waitingTotal + busyTotal` 已经是截断前的公开房全量。
- 新增私人房**聚合计数**。这是对既有契约的**有意修改**：
  `.trellis/spec/shared/backend/protocol-and-contracts.md` 现在写着「私人房间不计入
  `roomList` 的两个总数，这是『私人』二字唯一的技术含义」。改后的契约是：
  **私人房间的房间码、房间名、房主昵称、状态永不下发；只下发一个聚合数量。**
  聚合数量不能定位到任何一个具体房间，也不缩短 32^6 房间码的枚举成本。
- 同时下发「私人房是否开放」，供前端决定建房弹窗的表现。前端拿到的只是 UX 输入，
  **服务端仍必须独立校验**。

### R4 · 大厅展示

- 房间列表标题行显示两类占用：`公开 3/50 · 私人 2/20`，另起一行保留现有的
  `等人 2 · 进行中 1`。两个维度（可见性 / 能不能加入）不混在一行。
- 屏幕阅读器摘要（现有的 `sr-only` + `aria-live`）同步更新，说得出上限。
- 建房弹窗：私人房关闭时，私人选项**保留但置灰**（`disabled`），并给一行说明
  「本站已关闭私人房间」。玩家应当知道有这个能力、只是被关了。
- 分母取 `min(分类上限, 全局总闸)`，任何时候都不显示一个实际达不到的数字。

### R5 · 文档

`DEPLOY.md` 的环境变量表与「房间配额」一节、`.env.example` 同步三个新变量，
并写清「建议 `MAX_ROOMS >= MAX_PUBLIC_ROOMS + MAX_PRIVATE_ROOMS`」——
否则会出现「两类都没满却建不了房」的困惑（总闸先到顶）。

---

## Constraints

- **不改**：`@scg/game-core`、回合状态机、`apps/web/src/net/ws.ts`（透传层）、
  `ws/timing.ts`、`ws/quota.ts` 的按 IP 配额逻辑。
- `RoomQuotas` 的可注入性必须保住 —— `buildApp({ rooms })` 是 `Partial<RoomQuotas>`，
  新增字段不能让现有 3 个测试文件的注入写法失效。
- 私人房间的房间码/名称/房主/状态**依然一个字都不下发**。本次只放开聚合数量。
- 服务端仍是唯一权威：前端的置灰只是 UX，绕过它发 `private` 必须被拒。

---

## Acceptance Criteria

- [ ] 不配任何新变量时，行为与改动前完全一致（默认放行私人房，两类上限跟随 `MAX_ROOMS`）。
- [ ] `MAX_PUBLIC_ROOMS=1`：第 2 个公开房被拒且提示指明是公开房满，同一时刻仍能建私人房。
- [ ] `MAX_PRIVATE_ROOMS=1`：第 2 个私人房被拒，同一时刻仍能建公开房。
- [ ] `ALLOW_PRIVATE_ROOMS=0`：`visibility:'private'` 的建房被拒，提示为「本站不开私人房」
      而不是「满了」；漏传 `visibility` 的请求同样被拒（不降级为公开）。
- [ ] `MAX_PRIVATE_ROOMS=0` 与 `ALLOW_PRIVATE_ROOMS=0` 表现一致（同一条提示）。
- [ ] `MAX_ROOMS=0` 仍然关停一切建房，且提示是「服务器满了」而不是分类满。
- [ ] `roomList` 携带私人房数量与两类上限；私人房建立后公开列表条目数不变、
      `waitingTotal`/`busyTotal` 不变，只有私人计数 +1。
- [ ] 私人房的 `code` / `name` / `host` 不出现在任何一条 `roomList` 消息里（断言 JSON 全文）。
- [ ] 大厅在有 1 个公开房 + 1 个私人房时显示 `公开 1/N · 私人 1/M`。
- [ ] 私人房关闭时建房弹窗的私人单选项 `disabled` 且有说明文字，公开项仍可选。
- [ ] `pnpm -r typecheck && pnpm -r lint && pnpm -r test` 全绿；server 测试数量增加。
- [ ] `DEPLOY.md` / `.env.example` 含三个新变量与总闸关系的说明。

## Notes

- 这是一次**协议扩展 + 契约修订**：`shared` 的 spec 明确写过「私人房不计入总数」，
  改完必须回到 3.3 更新那一段，否则下一个人会照着旧 spec 把新字段当 bug 删掉。
- 决策记录（本轮与用户确认）：① `MAX_ROOMS` 保留为总闸；② 关闭私人房时选项置灰而非隐藏；
  ③ 展示口径为「公开 x/N · 私人 y/M」。
